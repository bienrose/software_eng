# AIMS database schema

This folder contains the relational schema for **MySQL 8.0.16 or later**. The Next.js server uses `mysql2` and the `DB_*` environment variables to connect to the `aims_db` database.

## Files

- `schema.sql` creates the core tables, constraints, indexes, and triggers.

## Core and adaptive data model

The core model keeps stable inventory facts in columns: category, item code, name, unit, on-hand quantity, and reorder level. The `reorder_level` column remains an operational stock threshold used by low-stock and replenishment logic, but new schema generation does not add it to the generated core-field list. Inventory movement history is recorded in `inventory_transactions`; a trigger updates on-hand quantity, rejects stock-outs that would make it negative, and records the resulting balance. Transaction rows are append-only; record a compensating movement to correct an earlier entry.

Adaptive fields are stored as versioned metadata:

1. Create an `inventory_categories` row.
2. Create an `inventory_schema_versions` draft for that category.
3. Store each generated field in `inventory_schema_fields` with a key, label, type, required flag, options, and validation rules.
4. Review the generated field definitions, then publish the version by setting its status to `active` and `published_at`. When replacing an active version, retire the old version and activate the new one in the same transaction.
5. Store values for those fields in each item's `custom_attributes` JSON object, keyed by `field_key`.

For example, a medical-supplies item could use:

```json
{
  "expiration_date": "2027-06-30",
  "batch_number": "MED-2026-001",
  "supplier": "Supplier A"
}
```

The item retains the schema version that defines its custom attributes. To change a category's fields, create and validate a new draft version; do not rewrite a published version. The database stores declarative field metadata instead of running SQL generated from user text. The application should validate `custom_attributes` against the item's schema version before saving.

## XGBoost records

`demand_predictions` supports either classification (`low`, `moderate`, or `high` demand) or regression (a predicted quantity). The selected mode, target definition, thresholds, features, and evaluation metrics still need to be finalized from the study's actual dataset and approved methodology.

## Apply

Run `schema.sql` using the MySQL command-line client or a SQL editor that supports the `DELIMITER` directive. It creates `aims_db` if it is missing, selects it, then creates any missing tables and creates or refreshes the triggers. Existing tables are left in place. The script also adds the `display_labels` column and check constraint to databases made from the earlier schema version. UUID values are generated by the application and stored as `CHAR(36)`.

You can rerun the script without errors for tables and triggers that already exist. `CREATE TABLE IF NOT EXISTS` does not change existing table definitions, though. When a future schema change adds or changes columns or constraints, include an idempotent `ALTER TABLE` step in this file; simply rerunning the table definition will not apply it. Back up important data before applying schema changes.

## Connect the Next.js app

1. Copy `.env.local.example` to `.env.local` in the project root.
2. Set `DB_USER` and `DB_PASSWORD` to the credentials used by your local MySQL server. Keep `.env.local` private; it is ignored by Git.
3. Confirm MySQL is running and apply `database/schema.sql` to create the tables.
4. Restart `npm run dev` after changing environment variables.

The API reads inventories, schema fields, items, and transactions from MySQL. It does not fall back to demo records when the database is unavailable; the pages show a database configuration or connection error instead.

MySQL runs DDL statements with implicit commits, so if an error interrupts first-time setup, inspect which objects were created before rerunning the script.

## Design assumptions

- The eventual database is MySQL 8.0.16+; the project previously had no configured database engine.
- One user account has one application role (`admin`, `inventory_manager`, `staff`, or `viewer`).
- Each item belongs to one category and one schema version.
- Existing item fields stay stable, while category-specific fields are stored in JSON and defined by schema metadata.
- Schema generation produces drafts that must be reviewed before activation.
- The application generates UUID v4 IDs and validates custom values against the item's schema version.
